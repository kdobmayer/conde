# Design partner review of DESIGN-v2.md at 780c6b6

Not ready to build yet. The architecture matches my proposal and the owner's choice: permanent local SQLite, explicit participation, no public lookup fallback, opaque shared mailboxes, and shared messages remaining on their shared board. I support those decisions. The blockers are missing lifecycle and boundary contracts that V1 and V2 would otherwise invent independently. This is my design review, not a Sol implementation panel; nothing was implemented or deployed.

Priorities below refer to the committed design. Current code was inspected only to verify compatibility claims and concrete failure paths.

1. **P1 — Publication and migration need a durable recovery protocol, not just server idempotency.** Lines 146–155 call the server and then create the local publication. If the server commits and the response is lost, or the daemon crashes before the local write, the mailbox is published remotely but has no local mapping. Reconciliation only specifies deleting stale local rows; it cannot reconstruct which local agent an orphan remote mailbox belonged to, especially with `--as`. A notification arriving in this gap is permanently `refused` under lines 161–162. “Fails cleanly” is therefore not established.

   Persist a local operation intent, selected local agent, board identity, and operation/idempotency key before the first remote mutation. Add a preparing/publishing state; persist the remote result and complete activation locally. Recover the same operation after a restart. Do not treat a known publication-in-progress as a permanently refused recipient; either keep routing inactive until activation or defer such jobs. Specify repeat publication with a different `--as`, and concurrent publish/unpublish semantics.

   The same requirement is essential for `host.migrate_v2` at lines 285–294. Server idempotency is useful only if the daemon retains the original key and can fetch the exact pre-conversion manifest after its next start. Otherwise the server has already removed the harness bindings and disabled v1 before the local copy exists. Persist the migration intent first; replay/import its manifest atomically and idempotently. Include local pin preservation and explicit handling of restored-name conflicts rather than an unconditional “newer address wins.” Fence the old host connection during conversion, not merely future v1 hellos. These are local operational records, so “no other local table changes” must not prevent implementing them.

2. **P1 — A stable mailbox also needs an opaque delivery incarnation and an explicit takeover boundary.** Lines 157–179 check mailbox ID plus publication state and report availability as a set of mailbox IDs. Replace a Claude session while keeping its local agent name: the old and new sessions can both be live during replacement, so that set never changes. The server's old held attempt remains attached to an apparently unchanged endpoint and cannot discover that it should retry against the new session. Its mailbox binding version has not changed either. Extending `gone_claude_holds` by kind does not solve this; that query currently notices a missing endpoint, not a replacement behind an unchanged endpoint.

   There is also no way for the old host to reject a queued job after another host takes its mailbox: reconciliation runs only on connect, and host-wide bridge fencing is not mailbox takeover. Likewise, an offline `unpublishing` operation could later unbind a mailbox that has since moved unless the server checks the expected host and generation.

   Define a publication/route generation and an opaque local binding incarnation, neither containing a session ID. Return/retain the route version, use the existing `Notify.binding_version`, and require expected ownership/generation on unpublish and takeover. Specify how the old host learns revocation and when takeover is considered complete. Define an honest race boundary: work injected before revocation is observed cannot be recalled. G5 cannot promise instantaneous cross-machine revocation from a connect-only reconciliation rule. Add gates for local session replacement without a disconnected interval, delayed old receipts, takeover with an already queued notify, and unpublish/re-publish of the same mailbox.

3. **P1 — Sanitization must cover automatic error metadata, not only actors and endpoint lists.** Lines 139–143 promise that a harness address never leaves the machine, but the reused notifier produces strings such as `no live Claude session {session_id}` and `cannot deliver to {socket path}` (`crates/conde/src/harness.rs`, Claude delivery path), and Codex failures propagate their error strings. The existing delivery loop sends failure reasons through `BridgeClient.report`. Translating the actor to a mailbox does not prevent those reasons from uploading session identifiers or local paths. A published agent should not disclose its internal endpoint just because delivery failed.

   Define a closed wire vocabulary for automatic outcomes, with detailed transport diagnostics retained locally. Render remote notification text from the validated structured fields; never fall back to arbitrary v1 text on a v2 connection. Audit automatic discovery, doctor/profile/pin fields, errors, and RPC envelopes as well as successful actor translation. Extend the capture gate to failed deliveries and reconnects of published agents, using distinctive local IDs/paths that must not occur on the wire. This restriction concerns conde-generated metadata; it does not require filtering the user's intentionally shared message text.

4. **P1 — Isolate remote backpressure and failure from local delivery.** The single notifier is appropriate, but lines 167–173 do not specify scheduling or outcome queue boundaries. In the existing cloud delivery loop, a full report budget causes the delivery worker to wait and retry. Reusing that behavior in the sole local/shared worker would stop local pushes when one remote board cannot accept outcomes. A permanently fenced/revoked remote connection must also stop that connection only, not the permanent local daemon.

   Give each origin bounded queues, independent retry/outcome handling, and fair delivery scheduling. Do not hold a local SQLite transaction or the notifier worker while awaiting a remote RPC, reconnect, report budget, or acknowledgment. Expand G1 beyond an unreachable server: exercise a connected server that stops acknowledging outcomes, a full remote queue, and revoked/fenced credentials while local delivery continues. Aggregate view calls should fetch remotes in parallel and specify how local results remain prompt; the two-second aggregate timeout at lines 77–81 currently conflicts with G1's literal “no added wait” for inbox. Either stream local results or state the bounded aggregate wait separately from local-operation latency.

5. **P2 — Scope receipt routing and references by immutable board identity.** The proposed `attempt_id -> origin` map at line 170 merges independent authorities into one keyspace. A duplicated/restored board or an untrusted remote can supply an attempt ID already used locally or by another board; the common notifier also derives its harness message identity from that ID. This can misroute receipts or suppress an unrelated push. Key transport tokens and routing by `(board identity, attempt ID)` and keep any transport encoding local; forward only the original board-local ID to that board. State recovery/retention behavior for delayed receipts and pending outcomes after restart.

   Similarly, publication rows and qualified references currently use only a mutable alias backed by a credential file. Pin an alias to a board authority/account identity and refuse silently replacing that identity during enrollment. A stable board ID in `board.info` is preferable; for the first board, prohibiting alias retargeting is a smaller adequate rule. Keep the friendly `dakai:` spelling. There is no need to implement federation. G6 should demonstrate deduplication at specified crash points; a restart between two completed exchanges is useful smoke coverage, not evidence of exactly-once delivery across injection/receipt crashes.

6. **P2 — Mailbox receipt semantics are not unchanged by removing the harness kind.** Lines 119–121 say receipts work unchanged. Currently `HarnessNotifier` returns `accepted` for Codex injection and provisional acceptance for Claude, while fleet/receipt paths special-case a Codex address to recognize successful reach. A shared row of kind `mailbox` loses that distinction. Specify what the daemon reports for confirmed Codex acceptance, queued Codex delivery, provisional Claude acceptance, and later Claude receipts. Normalize to common shared statuses locally or provide another explicit contract; do not infer the harness from the mailbox on the server. Test both harness flows, not just message exchange between two mailbox names.

7. **P2 — Fix the history order and importer contract before making the migration executable.** H2 correctly runs before local traffic. H3 then proposes importing a class-(b)-only maildir after the switch, with lane H explicitly scheduled afterward (lines 317–319,372–376). The current `channels_with_native_posts` (`crates/conde/src/import.rs:975–989`) refuses a target channel whenever it contains any message absent from that import source. That can include already restored kond messages even before new local traffic, and certainly includes post-switch messages. The proposed second import therefore cannot generally work as described.

   Choose either a combined, validated restore source before enabling local writes or a deliberately designed incremental importer with cursor and identity reconciliation. A one-off direct copy may be smaller than adding a general `conde export` command solely to feed a format adapter, but it still needs a documented validation and recovery contract. Preserve or explicitly map IDs, reply links, read state, and attachment content; file counts and attachment sizes alone are not integrity validation. Use hashes where exact copies are intended.

   Move H1 before migration and restore planning. Channel/member/agent listings do not prove that none of 346 imported agent IDs acquired cross-owner DMs after import. Compute the publication candidates from actual message relationships and distinguish the imported snapshot from later central changes. Freeze or revalidate the row manifest before cutover/retirement; deleting a channel must not cascade into newer shared traffic outside the approved list. Do not infer privacy or consent solely from current channel membership. The old cloud copies remain cloud-visible until a separately authorized retirement; unbinding names does not erase them.

These changes should be resolved in V0's contract, especially operation recovery, route generations, wire outcome semantics, and per-board task ownership. V0 should finish before the implementation lanes start relying on incompatible assumptions. The architecture itself does not need to be replaced.

On the numbered decisions: keep human-controlled publication and self-unpublication, stable mailbox IDs, board-qualified message references, no shared-history copy, and SQLite-only local state. Keep local and shared renames independent, but make `whoami` show both names. Accept `dakai` as a suggested alias, never an identity or permission grant. Replace automatic traffic-based migration with a reviewed preflight manifest plus a resumable operation; historical shared use is a useful candidate rule, not adequate evidence by itself.

What is more than the immediate requirement needs: full support for many boards can follow the first local-plus-central implementation, though all keys and interfaces should be scoped correctly now. Keep private cross-device cloud boards, tenancy, caches, auto-publication, and default-public lookup out of this increment. The read-only owner web view is a separately authorized L9 feature and should stay there. Do not make a reusable export product a prerequisite unless the selected recovery path actually needs one. A second ritual confirmation for the identical H4 list adds no architectural protection; one explicit approval of a concrete verified manifest is sufficient unless the owner specifically requests two. No destructive action is authorized or proposed for execution by this review.

Small surface clarifications before V3: reject an explicit remote board on local-only register/rename rather than silently ignoring it; decide whether `--board X inbox` overrides aggregation; define bare references consistently for CLI and MCP; and make publication state `unpublishing` block outbound mailbox use as well as inbound delivery. These need a single contract, not a separate product feature.

My acceptance remains the owner's actual requirement: unplugging or losing the shared service does not impair local collaboration; enrollment exports no local inventory; only explicitly enabled shared personas have routes; and every automated field crossing the boundary is scoped and intentional. With the lifecycle and migration amendments above, this is the design I would build.
